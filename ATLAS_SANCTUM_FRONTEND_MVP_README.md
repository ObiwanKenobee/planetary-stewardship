# Atlas Sanctum — Frontend MVP

## The Visual Operating System of Planetary Stewardship

> **Intelligence For A Thriving Planet**

From a mythic engineer perspective, the Atlas Sanctum poster is not merely a marketing page.

It is the **visual operating system of Atlas Sanctum**.

The frontend MVP should feel like the user is standing inside a living intelligence system that watches over a river, city, ecosystem, or nation.

This is not simply software for displaying dashboards.

It is an interface for **seeing reality, understanding change, coordinating action, and making regeneration measurable**.

---

Atlas Sanctum transforms places from passive locations on a map into **living systems of intelligence and action**.


# 3. Frontend Architecture

## Layer 1 — The Portal

### Purpose

The landing page is the gateway into Atlas Sanctum.

It should not read like a conventional SaaS homepage.

### Primary headline

> **Intelligence For A Thriving Planet**

### Background concept

Use a cinematic planetary visualization featuring:

- Earth from orbit
- River systems glowing through continental landscapes
- Data streams moving through ecosystems
- Cities, forests, rivers, and communities connected by light
- Subtle atmospheric motion
- A visual sense of scale from local node to planetary network

### Desired emotional response

The user should immediately understand:

> **This is bigger than software.**

The page should communicate scale without sacrificing legibility or product clarity.

### Portal content

```text
ATLAS SANCTUM

Intelligence For A Thriving Planet

Observe the living world.
Understand what is changing.
Coordinate action.
Verify what was restored.

[ ENTER THE ATLAS ]
```

### Motion language

Use motion to communicate **systems**, not decoration:

- Flowing data
- Pulsing network nodes
- Expanding geographic connections
- Slow orbital movement
- Environmental state transitions
- Real-time metric updates

Avoid excessive animation that makes the interface feel like a game trailer rather than an operational system.

# 6. Layer 4 — Atlas Oracle

## The Intelligence Layer

Atlas Oracle is the AI interface between observed reality and coordinated action.

The interaction should feel fundamentally different from a generic chatbot.

It should feel like a **planetary intelligence console**.

### Example questions

```text
What threatens this river?

What has changed in the last 90 days?

Where is restoration having the greatest effect?

Which communities are most exposed to flooding?

What should we verify next?
```

### Example responses

```text
Vegetation density has increased 34%.

Waste accumulation detected along the eastern corridor.

Flood risk is elevated for the lower watershed.

Three restoration sites require field verification.
```

Every AI response should ideally distinguish:

```text
Observation
Inference
Forecast
Recommendation
Evidence
Confidence
```

This protects the system from presenting predictions as facts.

### Oracle design principle

The Oracle should feel less like:

> "Ask me anything."

and more like:

> **"Here is what the living system is telling us."**

### Trust model

# 13. Frontend Design Language

## Visual Philosophy

The interface should feel like:

**Earth × Observatory × Civilization × Intelligence System**

### Design principles

#### 1. Spatial first

Geography should be visible whenever place matters.

#### 2. Evidence before abstraction

Show the satellite image, field photograph, sensor reading, or observation before presenting a synthesized conclusion.

#### 3. Living state, not static dashboard

Interfaces should communicate change:

```text
Stable
↓
Changing
↓
At Risk
↓
Intervention
↓
Recovering
```

#### 4. Mission over vanity

Metrics should explain what matters operationally rather than becoming decorative KPIs.

#### 5. Calm power

The interface should feel powerful without becoming noisy.

Use hierarchy, whitespace, controlled motion, and clear state transitions.

#### 6. Myth without deception

The visual language can be mythic.

The data must remain empirical.

Do not let cinematic presentation imply certainty that the underlying evidence cannot support.

# 15. Data Model Philosophy

Atlas Sanctum should model **the living system**, not merely the interface.

A useful conceptual graph is:

```text
Place
  ├── contains → Community
  ├── contains → River
  ├── contains → Ecosystem
  ├── contains → Project
  └── contains → Sensor

Observation
  ├── occurs_at → Place
  ├── produced_by → Human / Sensor / Satellite
  ├── supports → Insight
  └── contributes_to → Impact Event

Project
  ├── targets → Place
  ├── executes → Intervention
  ├── produces → Outcome
  └── verified_by → Verification Record

Oracle Insight
  ├── based_on → Evidence
  ├── references → Place
  ├── has_confidence → Confidence Score
  └── suggests → Action / Verification
```

This creates a foundation for a later **Atlas Economic Graph** and **Opportunity Graph** without forcing those systems into the first MVP.

# 16. AI Safety and Evidence Rules

The Atlas Oracle should never silently convert uncertainty into fact.

### Every AI-generated insight should ideally expose

```text
Claim
Source
Timestamp
Model
Confidence
Evidence
Known Limitations
```

### Example

Instead of:

> Flooding will happen in 21 days.

Prefer:

> Forecast model estimates elevated flood risk within the next 21 days under current rainfall and river-level assumptions.

Then show the evidence and model context.

### Principle

> **The Oracle interprets reality. It does not replace reality.**

# 24. Technical Principles

### Type safety

TypeScript should cover domain objects, API contracts, map events, Oracle responses, and verification states.

### Component boundaries

Separate:

```text
Presentation
↓
Domain Logic
↓
Data Access
↓
External Services
```

### Provider abstraction

Keep mapping, AI, geospatial, and sensor providers behind replaceable interfaces where practical.

### Auditability

Every material state change should generate a traceable event.

### Offline resilience

Field workflows should eventually support unreliable connectivity, particularly for community and ranger operations.

### Accessibility

The mythic visual layer must not compromise usability, contrast, keyboard navigation, semantics, or readable information hierarchy.
